An agent never does I/O itself. When it needs something from the world, such as
a model's reply, a web page or a timer, it **declares an effect**: a description
of the work, as data. A **handler** does the work, and its result comes back to
`step` as a [message](/concepts/messages).

This page follows one agent: a chat agent whose replies come from a model, and
can be stopped partway.

```ts title="src/agent.ts"
import type { Agent, NoConfig } from '@acentric/types';

type Replying = { key: string; prompt: string; stop: boolean };
type Snapshot = { replying: Replying | null };

/** The effects this agent asks for, by kind. */
export type ChatKinds = {
  reply: { args: { prompt: string }; result: { text: string } };
};

const agent: Agent<Snapshot, NoConfig, ChatKinds> = {
  name: 'chat',
  version: '0.1.0',
  kinds: ['reply'],

  init: () => ({ snapshot: { replying: null } }),

  step: ({ snapshot }, message) => {
    const { replying } = snapshot;
    if (message.type === 'input' && message.kind === 'say') {
      const text = message.payload['text'];
      if (typeof text !== 'string') return { error: 'say needs some text' };
      if (replying !== null) return { error: 'still replying: send stop first' };
      const key = `reply:${message.id}`;
      return {
        snapshot: { replying: { key, prompt: text, stop: false } },
        append: [{ kind: 'user', body: text }],
      };
    }
    if (message.type === 'input' && message.kind === 'stop') {
      if (replying === null) return { error: 'nothing to stop' };
      return { snapshot: { replying: { ...replying, stop: true } } };
    }
    if (message.type === 'effect') {
      const { outcome } = message;
      const stopped = replying?.stop ?? false;
      return {
        snapshot: { replying: null },
        append: [
          'ok' in outcome
            ? { kind: 'assistant', body: { text: outcome.ok.text, stopped } }
            : {
                kind: 'reply_failed',
                body: 'failed' in outcome ? outcome.failed.code : 'interrupted',
              },
        ],
      };
    }
    return { snapshot };
  },

  effects: ({ snapshot }) => {
    const { replying } = snapshot;
    if (replying === null) return [];
    const { key, prompt, stop } = replying;
    return [{ key, kind: 'reply', args: { prompt }, abort: stop }];
  },
};

export default agent;
```

```ts title="src/handlers.ts"
import type { HandlersFor } from '@acentric/types';

import type { ChatKinds } from './agent.js';
import { streamReply } from './model.js';

const handlers: HandlersFor<ChatKinds> = {
  reply: {
    mode: 'reissue',
    timeoutMs: 120_000,
    run: async ({ args, signal, secrets }) => {
      const apiKey = await secrets.get('MODEL_API_KEY');
      let text = '';
      for await (const delta of streamReply(args.prompt, apiKey, signal)) {
        text += delta;
      }
      // Finished or stopped, what was written so far is the reply.
      return { text };
    },
  },
};

export default handlers;
```

`streamReply` stands in for a model provider's client. Real code would call
the provider's SDK here:

```ts title="src/model.ts" check
/** Streams a reply word by word, until it ends or `signal` fires. */
export async function* streamReply(
  prompt: string,
  apiKey: string,
  signal: AbortSignal,
): AsyncGenerator<string> {
  if (apiKey === '') throw new Error('no API key');
  for (const word of `You said: ${prompt}`.split(' ')) {
    if (signal.aborted) return;
    await new Promise((resolve) => setTimeout(resolve, 50));
    yield `${word} `;
  }
}
```

## Declaring effects

`effects(state)` returns every effect the agent wants running **now**: the
whole list, every time. The agent never says "start" or "cancel". The runner
calls `effects` after every step and compares the list with what is running:

| When the list…                  | The runner…                                   |
| ------------------------------- | --------------------------------------------- |
| has a key it is not running     | starts it                                     |
| still has a running key         | leaves it alone, even if its args changed     |
| no longer has a running key     | cancels it, and its result is never delivered |
| marks a running key `abort`     | stops it, and delivers what it returns        |
| has a key that already finished | ignores it                                    |

This is React's render again: you describe what should exist, and something
else works out the changes. A runner recovering from a crash does the same. It
calls `effects` on the saved state, and the list says what should be running.

`effects` takes no `now`. The list must depend on the state alone, so the
runner gets the same answer whenever it asks, including after a restart. To run
something at a time, a step computes the time once and stores it, and `effects`
copies it out, as the [reminders agent](/concepts) does.

## Keys

The agent chooses each effect's key, and a key is used once. When its result
has been delivered, the key is finished, and declaring it again does nothing.
New work needs a new key, which is why the chat agent builds its key from the
input's id: each message gets a reply of its own.

A key may appear only once in a list. Declaring the same key twice is a bug,
and the step that led to it fails.

## Cancelling and aborting

There are two ways to stop an effect, and they differ in what comes back.

- **Cancel**, by dropping the key from the list: the effect is stopped and
  forgotten. Use it when the result no longer matters, like the
  [weather agent's](/concepts/messages) replaced lookup.
- **Abort**, by keeping the key and marking it `abort: true`: the effect is
  stopped, and whatever the handler returns is still delivered. Use it when
  partial work is worth keeping, like a reply cut off mid-sentence.

The chat agent's `stop` input marks its reply `abort`, so the half-written
reply still lands in the log. An abort cannot be undone: once set, the
handler's signal has fired.

## Handlers

A handler is the only code that does I/O. Each one runs one kind of effect, and
receives a context:

| Field               | What it is                                                                  |
| ------------------- | --------------------------------------------------------------------------- |
| `args`, `key`       | What the agent declared. The key also makes a good idempotency key for APIs |
| `signal`            | Fires on cancel, abort or timeout. Pass it to whatever does the I/O         |
| `secrets.get(name)` | Reads a secret, from wherever the runner keeps them                         |
| `log.list(query)`   | Reads any part of the session's log, beyond the step's window               |
| `attempt`           | 1 on the first run, higher when it runs again after a crash                 |

A handler depends only on its args: anything it needs from the agent's state,
`effects` copies into them. Secrets are the exception, because args and state
are stored, so a handler asks for a secret by name.

Handlers live apart from the agent: in their own file, and in the local runner,
their own process. That keeps the agent pure, and lets `acentric build` check
that it is.

## Reissue and once

Every handler says what should happen if the runner crashes while it is
running:

- `reissue`, at least once: run it again. For work that is safe to repeat, such
  as a model call or a search.
- `once`, at most once: never run it again, and deliver `interrupted` instead.
  For work that must not happen twice, such as sending an email or making a
  payment.

A request can override its handler's mode with `mode`. A `reissue` effect that
keeps being cut off gives up after a limit, 5 runs by default, with
`attempts_exhausted`.

## Reading older history

A handler can read the whole log, so a step reaches history before its
[window](/concepts/state#the-window) through an effect. A chat agent that
summarises declares a `summarise` effect; its handler reads the old turns with
`log.list` and asks a model for a summary; and the step appends the summary and
moves its window to start there.

## Runner kinds

Some kinds come from the runner, not from you. Their names start with `@`, so
they never clash with yours. Both runners provide `@timer`, which fires at a
time you give it. Add a runner's kinds to your own map with its type, such as
`LocalRunnerKinds`.

The local runner can also take kinds from the app connected to it. The agent
cannot tell those apart from its own handlers.

## When a handler fails

A failed effect arrives with a `code`:

| Code                 | Meaning                                        |
| -------------------- | ---------------------------------------------- |
| `threw`              | The handler threw                              |
| `timeout`            | It ran past its time limit                     |
| `aborted`            | It was aborted, and threw instead of returning |
| `invalid_result`     | It returned something that is not JSON         |
| `unknown_kind`       | No handler exists for the kind                 |
| `attempts_exhausted` | A `reissue` effect was cut off too many times  |
| `limit_exceeded`     | It went over a runner limit, such as args size |

The step decides what a failure means: try again with a new key, tell the user,
or give up. A failure is an ordinary message, so handling it is ordinary code.
The chat agent logs it.
