A runner takes an agent and runs sessions of it. Runners can be very different:
in memory for a test, on your laptop with a SQLite file, across a fleet of
servers, in one Durable Object per session. They all follow one contract, so an
agent behaves the same on every one of them.

## What every runner promises

Every runner runs the same loop for each session:

1. Take the next message.
2. Give it to `step`, with the session's state and a `now`.
3. Save everything `step` returned at once: the snapshot, the log entries, the
   change to the effects, and the message marked as delivered.
4. Match the effects the agent now declares with those running.
5. Run handlers, and turn what they produce into new messages.

And every runner keeps the same promises:

- **One message at a time** per session.
- **All or nothing.** A step's result is saved whole, or, if the step fails,
  not at all. Log entries are numbered 1, 2, 3 with no gaps.
- **Time never goes backwards** for a session, even across machines.
- **State changes only through your code:** `init`, `step` and `migrate`. A
  runner never edits a snapshot, invents an input id or makes up an effect key.
- **The same recovery.** Within what a runner keeps, a crash looks the same
  everywhere: saved steps are never lost or applied twice, an unsaved message is
  delivered again, a running `reissue` effect runs again, and a running `once`
  effect is reported `interrupted`.
- **No extras in the model.** A runner cannot add message types or fields.
  Anything it offers an agent comes as an `@` kind.

## What runners choose

Everything else is the runner's choice, and that is where runners differ:

| Area                   | For example                                              |
| ---------------------- | -------------------------------------------------------- |
| Storage and durability | Memory, files, SQLite, Postgres                          |
| Where handlers run     | The same process, child processes, containers            |
| Built-in kinds         | `@timer`, or others                                      |
| How callers reach it   | Function calls, a protocol over stdio or WebSocket, HTTP |
| Limits and defaults    | Sizes, time limits, attempts, the window                 |
| Policies               | What follows a failed step, upgrades, keeping the log    |
| Journal                | Keeping what each session received, for replay and forks |
| Secrets and security   | Environment variables or a vault; who may send what      |

Each runner says what it keeps and what survives: nothing past the process, a
process crash, or the loss of a machine.

## The memory runner

`@acentric/runner-memory` keeps everything in memory and runs handlers in the
same process. Use it for tests, scripts and trying an agent out. Nothing
survives the process.

```ts title="try.ts" run
import { createMemoryRunner } from '@acentric/runner-memory';
import type { Agent } from '@acentric/types';

const counter: Agent<{ count: number }> = {
  name: 'counter',
  version: '0.1.0',
  init: () => ({ snapshot: { count: 0 } }),
  step: ({ snapshot }, message) =>
    message.type === 'input' && message.kind === 'add'
      ? {
          snapshot: { count: snapshot.count + 1 },
          append: [{ kind: 'added', body: null }],
        }
      : { snapshot },
  view: ({ snapshot }) => ({ count: snapshot.count }),
};

const runner = createMemoryRunner();
const { id } = runner.create(runner.load(counter), {});
if (id === undefined) throw new Error('the session was not created');

await runner.input(id, 'add', {}); // answered once its step is saved
await runner.input(id, 'add', {});
console.log(runner.view(id)); // { count: 2 }
console.log(runner.log(id).map((entry) => entry.seq)); // [ 1, 2 ]
runner.close();
```

## The local runner

`@acentric/runner-local` is for your own machine or a single server:

- **Sessions survive restarts.** They are kept in SQLite or in plain files.
- **Handlers run in child processes,** so one that crashes or hangs takes down
  only its own process.
- **Apps reach it from any language.** It speaks a JSON-RPC protocol over stdio
  or WebSocket, and `@acentric/client` speaks it from TypeScript.
- **Code is deployed into the store,** and sessions can be upgraded to new
  versions of it.
- **A failed step stops its session** until an upgrade fixes the code.
- **Every session keeps a journal,** so it can be
  [replayed](/why/replay), and forked at any point.

In a project made by `npm create acentric`, the CLI runs it for you:

```sh
acentric dev     # rebuilds and hot-reloads on save, with a dev UI
acentric start   # runs the built agents
```

Or run it yourself, for an app to connect to:

```sh
acentric-runner --store sqlite:./agents.db --listen ws://127.0.0.1:7420
```

## Writing your own

Anyone can write a runner, in any language that can run JavaScript, for any
infrastructure. Nothing about Acentric assumes ours.

The contract is the loop and the promises above, and conformance tests check
it. `@acentric/conformance` holds them as scenarios, one JSON file each. A
scenario drives a small test agent, the probe, through messages and handler
outcomes, and says what must then be true: the answers, the log, the snapshot,
the effects running.

Your runner provides an **adapter**, which the scenarios drive:

| Adapter method                 | Does                                                 |
| ------------------------------ | ---------------------------------------------------- |
| `create`, `input`, `configure` | Creates the probe's session and sends it messages    |
| `release`                      | Finishes a probe effect, with a value or by throwing |
| `settle`                       | Waits until every message that can be delivered is   |
| `running`, `log`, `snapshot`   | Reads what the scenario checks                       |
| `crash`, `upgrade`             | Restarts the runner, or upgrades the session         |

A runner in TypeScript plays every scenario with `play`:

```ts title="conform.ts"
import { loadScenarios, play } from '@acentric/conformance';
import type { Adapter } from '@acentric/conformance';

/** Plays every scenario against a runner, opened afresh for each by `open`. */
export async function conform(open: () => Promise<Adapter>): Promise<boolean> {
  let passed = true;
  for (const scenario of await loadScenarios()) {
    const result = await play(scenario, open);
    console.log(`§${scenario.section} ${scenario.name}: ${result.status}`);
    if (result.status === 'failed') {
      console.log(`  step ${result.step}: ${result.problem}`);
      passed = false;
    }
  }
  return passed;
}
```

A runner in another language reads the same JSON files and plays them with a
small player of its own. A scenario that needs a feature your runner does not
offer, such as surviving a crash or upgrades, is skipped and reported, never
passed.

A runner that passes them all is as much an Acentric runner as ours. The memory
and local runners pass every scenario, including crashes and upgrades.

## Acentric Cloud

Acentric Cloud is coming: one easy way to host agents without running servers
yourself, with tools for watching and investigating sessions. It is a runner
like any other. It follows the same contract, passes the same tests, and runs
the same agents unchanged.
