Everything that happens to a session reaches `step` as a **message**, one at a
time. There are four types, and each one is something the runner itself does:

| `type`     | What happened                         | Sent by                 |
| ---------- | ------------------------------------- | ----------------------- |
| `input`    | A caller sent the session something   | Your app, a user, a CLI |
| `effect`   | An effect the agent declared finished | The runner              |
| `config`   | A caller changed the session's config | Your app                |
| `migrated` | The session was upgraded to new code  | The runner              |

Only those four exist. Anything else an agent understands, such as "pause" or
"steer", is an input with a kind the agent chooses.

This agent looks up the weather for a city, and its `step` handles all four:

```ts title="src/agent.ts"
import type { Agent } from '@acentric/types';

type Snapshot = {
  pending: { key: string; city: string } | null;
  last: { city: string; celsius: number } | null;
};
type Config = { units: 'C' | 'F' };
type Kinds = { lookup: { args: { city: string }; result: { celsius: number } } };

const agent: Agent<Snapshot, Config, Kinds> = {
  name: 'weather',
  version: '0.2.0',
  kinds: ['lookup'],

  init: () => ({ snapshot: { pending: null, last: null } }),

  step: ({ snapshot }, message) => {
    switch (message.type) {
      case 'input': {
        const city = message.payload['city'];
        if (message.kind !== 'check' || typeof city !== 'string') {
          return { error: 'send check with a city' };
        }
        return {
          snapshot: { ...snapshot, pending: { key: `lookup:${message.id}`, city } },
        };
      }
      case 'effect': {
        const city = snapshot.pending?.city ?? '';
        if ('ok' in message.outcome) {
          const { celsius } = message.outcome.ok;
          return {
            snapshot: { pending: null, last: { city, celsius } },
            append: [{ kind: 'checked', body: { city, celsius } }],
          };
        }
        const why =
          'failed' in message.outcome ? message.outcome.failed.code : 'interrupted';
        return {
          snapshot: { ...snapshot, pending: null },
          append: [{ kind: 'lookup_failed', body: { city, why } }],
        };
      }
      case 'config': {
        const units = message.config['units'];
        return units === 'C' || units === 'F'
          ? { snapshot }
          : { error: 'units must be C or F' };
      }
      case 'migrated':
        return {
          snapshot,
          append: [{ kind: 'upgraded', body: { from: message.from } }],
        };
    }
  },

  effects: ({ snapshot }) => {
    const { pending } = snapshot;
    if (pending === null) return [];
    return [{ key: pending.key, kind: 'lookup', args: { city: pending.city } }];
  },

  view: ({ snapshot, config }) => {
    if (snapshot.last === null) return { checking: snapshot.pending !== null };
    const { city, celsius } = snapshot.last;
    const temperature = config.units === 'F' ? (celsius * 9) / 5 + 32 : celsius;
    return {
      checking: snapshot.pending !== null,
      city,
      temperature,
      units: config.units,
    };
  },
};

export default agent;
```

## Inputs

An input has a `kind` and a JSON `payload`, both chosen by you. The weather
agent takes `check`; the notes agent takes `add`, `done` and `remind`.

Every input also has an `id`, chosen by the caller, so a runner can tell a
retry from a new input. The local runner keeps every id it has accepted:
sending the same id again gets the first answer back without running `step`
again, and sending it with a different payload is refused. The weather agent
uses the id in its effect's key, so each check gets a key of its own.

## Effect results

When a handler finishes, its result arrives as an `effect` message, with the
`key` the agent gave the effect and an `outcome`. The outcome is one of three:

- `ok`: the handler returned a value.
- `failed`: it did not succeed. Its `code` says why, such as `threw`,
  `timeout` or `unknown_kind`, and `error` holds the detail.
- `interrupted`: a crash cut off a `once` effect, which is never run twice. It
  may or may not have done its work.

With a typed map of kinds, as `Kinds` above, each result has its handler's
type: `message.outcome.ok.celsius` is a number.

An effect the agent stops declaring is cancelled, and its result is never
delivered. If the weather agent is asked to check a second city before the
first answer arrives, the first lookup is no longer declared, so it is
cancelled, and only the second result reaches `step`. The
[Effects page](/concepts/effects) covers this in full.

## Config changes

A `config` message carries the new config. During that step, the state still
holds the current config, so the step can compare the two, such as to log what
changed. A step can accept the new config, often by returning its snapshot
unchanged, or reject it to keep the current one. Once accepted, the new config
is in the state for `effects`, `view` and every later step. The weather agent
accepts only units it knows, reading them from the message.

## After an upgrade

When a session moves to a new version of the code, the runner calls the new
version's `migrate`, then delivers `migrated`, with `from` naming the old
version. It is the new code's first message: a chance to log the upgrade, or
to restart work the old version left behind.

The log is not migrated, so new code must still read the entries old code
wrote.

## Rejecting a message

A step can refuse an `input` or a `config` change by returning `{ error }`.
Nothing changes and nothing is logged, and the caller gets `error` back as
the answer:

```ts
return { error: 'send check with a city' };
```

A rejection is an answer, not a failure. A step that throws, or returns
something that is not JSON, has failed instead, and nothing it returned is
applied either.

`effect` and `migrated` messages have no caller to answer, and dropping an
effect's result would lose it for good, so rejecting one, or failing on one,
is a bug. Because the step is pure, it would fail the same way again. The
local runner stops the session until an upgrade fixes the code.

## Time

`step` never reads the clock. The runner passes the time as `now`, in
milliseconds, and stamps it on the log entries that step appends. To act
later, keep a time in the snapshot and declare a `@timer`, as the
[reminders agent](/concepts) does.

`now` never goes backwards. A runner never gives a step a time earlier than
the session's last log entry, even if the machine's clock moves back, so a
deadline computed from `now` stays after the step that set it.
